# x264 生产编码迁移

生产 H.264 编码统一使用已发布 schema 4 SDK 中的 x264。OpenH264 仅供视频库解码夹具和 SDK 完整性检查使用；FreeRDP 继续使用自己的 OpenH264／libyuv。第三方归档及 SDK 清单没有改动。

## 接口与配置

固定 `superfast + zerolatency`、Constrained Baseline、Annex B、切片线程、无 B 帧／lookahead。默认线程预算为 `min(GOMAXPROCS, 16, 宏块行数/4)`，至少为 1；`Config.Threads` 可显式指定 1–16。创建后的线程数以 `Encoder.Info()` 为准，不在连接中自动调整。

ABR bitrate 与 VBV maxrate 相同，VBV 容量为 250ms 且不少于一个配置帧周期。关闭 filler 和 HRD，不为填满带宽发送无效内容。bit/s 转 kbit/s 向下取整。GOP 为配置 FPS 的两倍，关闭场景切换额外 IDR，保留调用方强制 IDR。

`UpdateRate` 已移除，调用方通过本次编码的 `Options.Rate` 提交码率：

```go
out, err := encoder.EncodeBGRA(source, h264.Options{
    TimestampMS: timestamp,
    Rate: &h264.RateControl{Bitrate: 24_000_000, FPS: 60},
})
```

验证和像素准备完成后才提交 x264 重配；同次编码成功、访问单元完整且参数复核通过后才确认配置，不保留跨调用待应用参数。纯码率更新保持参考链。FPS 改变返回 `ErrReconfigureRequired`，FPS／尺寸／等级变化需要创建候选实例并确认完整 SPS／PPS／IDR 后替换。

编码前拒绝保留旧实例。进入编码后失败、未知延迟、参数不一致或访问单元超限使实例不可继续使用，返回 `ErrUnusable`，不伪称回滚。外部时间戳仍回传给调用方，内部使用独立递增帧号；RTP 时间线继续由现有发送层管理。

## 业务与交付

Backend 和 RDP 出站视频同步迁移原子更新接口。成功回执在编码后产生，配置与已完成帧绑定同一版本；取消或更新请求不能抛弃已完成参考帧。候选失败保留旧实例；帧率改变不再错误地报告参考链连续。

Core 的既有五秒汇总增加 `encoder_replacements`，用于区分编码耗时与上层策略引起的重建。画质自适应、输入、授权、P2P／中继限制、HDR 矩阵及客户端解码声明保持既有合同。RDP 协议没有新增连续性字段，旧适配仍采用保守行为。

发布时先准备迁移后的公共视频库源码，再以同一源码锁构建 Core 与 RDP worker。运行二进制不需要视频库 DLL。无需重建第三方 SDK、Web 或 Android AAR／APK；回退使用上一套完整产品产物，不增加双编码器开关。

## 可重复验证

```text
python scripts/check.py --link --race
python scripts/check-coexist.py --rdp-sdk ../termous-rdp/sdk/windows/amd64
go test -run=^$ -bench=BenchmarkDesktopEncoding -benchtime=30s -count=3 ./h264
go test -run=^$ -bench=BenchmarkDesktopThreads -benchtime=30s -count=3 ./h264
go test -run=^$ -bench=BenchmarkHDRPipeline -benchtime=30s -count=3 ./color
```

正式性能测量单独执行，不与其他编码基准并行。动态素材由独立 `internal/testpattern` 生成；预热 120 帧，素材生成排除在编码计时外，包含周期 IDR。记录平均、P95、分配、请求 FPS 下的输出码率、访问单元峰值及输出比例；HDR 基准另分开记录转换和编码耗时。CPU／工作集观测需要同时注明是否包含素材生成。

轮次时长包含无分配的素材生成，`ns/op` 与 P95 由处理调用的独立计时计算，避免逐帧暂停 Go 基准计时器。桌面编码指标包含 BGRA→I420、编码和返回数据复制；HDR 指标另包含色彩处理，但均不包含 WGC 采集、网络或接收端解码。`Mbps-at-fps` 是按配置 FPS 换算的编码输出量，不是网络吞吐。

基准名称末尾的 Go 并发数不是编码线程数；实际线程以 `Encoder.Info()` 为准。CPU 进程计数包含造图与基准调度，Go 分配指标不包含 x264／libyuv／GPU 的原生内存，进程工作集用于补充观察。

Windows 本轮的详细日志和构建产物位于工作区 `TEMP/x264-migration`。迁移前基线使用旧生产适配的独立测试二进制；HDR 对照源从同一 Git 基线提取到 TEMP，并使用相同动态素材，不覆盖工作区源码。

## Windows 编码性能记录（2026-11-01）

测试机器为 Ryzen 9 7900X，Windows amd64，`GOMAXPROCS=24`。基线来自 `616641d` 的 OpenH264 生产适配；新实现采用默认 16 个切片线程。以下每格为三轮的平均耗时／各轮 P95 的平均值，单位 ms；P95 均值不代表合并全部样本后的 P95。每轮预热 120 帧、基准时长 30 秒，两版使用相同的滚动文字、移动窗口和彩色纹理素材。

| 分辨率 / FPS / Mbps | OpenH264 平均 / P95 均值 | x264 平均 / P95 均值 |
|---|---:|---:|
| 1080p / 30 / 24 | 12.53 / 15.95 | 2.59 / 3.28 |
| 1080p / 30 / 50 | 12.13 / 14.78 | 2.52 / 3.16 |
| 1080p / 30 / 100 | 12.98 / 15.68 | 2.48 / 3.13 |
| 1080p / 60 / 24 | 11.42 / 13.47 | 2.29 / 3.02 |
| 1080p / 60 / 50 | 12.27 / 14.73 | 2.64 / 3.29 |
| 1080p / 60 / 100 | 13.86 / 17.15 | 2.71 / 3.58 |
| 1440p / 30 / 24 | 21.30 / 25.27 | 3.92 / 4.51 |
| 1440p / 30 / 50 | 20.59 / 24.10 | 4.05 / 4.78 |
| 1440p / 30 / 100 | 20.77 / 25.18 | 4.18 / 4.97 |
| 1440p / 60 / 24 | 20.33 / 24.18 | 3.88 / 4.51 |
| 1440p / 60 / 50 | 20.01 / 22.92 | 3.99 / 4.61 |
| 1440p / 60 / 100 | 20.60 / 23.37 | 4.23 / 5.00 |

全部编码组合的平均和 P95 均通过“不回退超过 5%”门槛。x264 每个输入都有同步输出，未跳帧；1440p60／100Mbps 输出按配置帧率折算为 98.52–98.59Mbps，最大访问单元 964,368 字节，低于既有 4MiB 边界。该组合三轮实际 P95 为 5.001–5.002ms，编码部分进入 16.67ms 帧预算。

各组合均为每帧 2 次 Go 分配。满速、不限时隙运行时，x264 进程平均占用相当于 3.40–4.01 个 CPU 核，OpenH264 约 1 个；该数值含造图、预热和基准校准，且两版实际处理帧数不同，不能当作固定 60fps 的 CPU 对照。编码矩阵中进程工作集峰值分别约 149.94MiB／155.24MiB，不代表真实采集会话总内存。

同机另测 1440p60／100Mbps 的固定线程数，每种三轮，不在连接中自动更改线程：

| 实际编码线程 | 平均耗时（ms） | P95 均值（ms） |
|---|---:|---:|
| 1 | 15.05 | 17.34 |
| 4 | 6.53 | 7.52 |
| 8 | 4.96 | 5.63 |
| 16 | 4.09 | 4.85 |

所有线程组合均同步输出且未跳帧。该结果支持本机默认采用 16 线程，但不应推断所有机器的最佳线程数相同；低 CPU 预算仍受 `GOMAXPROCS` 约束，调用方可显式限制线程。

### HDR 转换加编码

两组均请求 100Mbps，使用默认色彩后端和相同动态 RGBA16F 输入；下表沿用三轮平均／P95 均值的口径。输出吞吐只按同步处理耗时计算，不含素材生成，也不是远控实际帧率。

| 合成模式 | OpenH264 总平均 / P95 均值（ms） | x264 总平均 / P95 均值（ms） | x264 转换均值（ms） | x264 编码均值（ms） | x264 处理输出（帧/秒） |
|---|---:|---:|---:|---:|---:|
| 1080p / 30fps | 26.78 / 32.13 | 18.54 / 22.26 | 15.47 | 3.07 | 52.45–54.73 |
| 1440p / 60fps | 53.72 / 63.25 | 30.83 / 37.90 | 26.17 | 4.66 | 32.28–32.54 |

两个 HDR 组合均通过 5% 回退门槛，但 1440p 的色彩转换本身仍超过 16.67ms。生产编码迁移已减少编码成本，当前完整 HDR 合成链路仍不能证明稳定 60fps；后续应单独定位既有上传、转换、同步下载的耗时，而不是继续提高码率上限。本轮没有改动 HDR 算法、设备选择或纹理传输。

基准结束后独立查询当前默认后端返回 `d3d11`，未回落至 `d3d11-warp`。该查询不代替逐阶段 GPU 计时，也不能据此推断具体显卡或 GPU 利用率；完整日志见 `TEMP/x264-migration/color-backend.log`。后续基准会在预热前记录后端和实际编码线程，便于对照环境。

## Windows 验证范围

本次在 Windows amd64 执行生产原生测试、OpenH264 连续解码夹具、适用的 race 检查和无 cgo 测试。覆盖独立 I420 stride、缩放、竖屏、SPS／VUI、24→50→100→24Mbps 连续更新、拒绝重配及应用后失败、FPS 候选替换，以及取消后的配置与参考帧交付。高码率序列在 1080p／1440p 各持续编码 64 帧动态素材，并以同一解码器验证参考链与独立灰阶期望；候选切换序列还覆盖 30／60／15fps 与 Level 4.0／5.1／3.1 的连续解码。既有颜色容差未放宽。

Backend 的本机桌面、媒体服务及 RDP 适配测试通过；RDP 原生测试及两种归档链接顺序的共存检查通过。Pion 回归验证一个访问单元中的 16 个大切片经过 FU-A 分包后可完整重组，时间戳与序号连续，结束标记仅位于访问单元末尾。

三个目标的 cgo 参数检查通过，Windows 生产编码测试产物包含私有 x264，未链接视频库的私有 OpenH264。SDK 工具回归完成 89 项：88 项通过，1 项因本机符号链接权限不足跳过。Core 与 RDP worker 完成原生构建、动态依赖检查，RDP worker 的隔离目录 RPC 启动、能力查询和退出检查通过。

合成解码、链接及性能结果不能代替 Windows HDR 桌面与 Electron／浏览器／Android 的真实连接验收。Linux／macOS 原生执行由对应 CI 验证；未执行的客户端和平台不得标记为通过。

## 实施后复查

复查修正了两处负载观测边界：本机桌面仅更新配置版本、有效参数未变时，保留当前帧的稳态处理样本；RDP 出站视频在编码完成时停止计时，不把配置回执的传输等待记作处理成本。两处均先用确定性回归复现失败，再验证修复。`encoder_replacements` 仅计实际替换，不包含首次创建。

补充 1／2／3fps 的 VBV 下限、跨越及未跨越 kbit/s 取整边界的码率更新，以及所有受支持 Level 的 SPS 声明回归。历史 OpenH264 验证记录明确标为历史边界，测试中的旧编码器和回滚描述已清理。上述调整不修改画质决策规则，也没有重跑或改写此前的性能基准数据。
